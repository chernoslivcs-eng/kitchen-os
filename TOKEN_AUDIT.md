## 3. Управління історією діалогу

- **chat**: стан зберігається в PG-таблиці `message` (сесійно). На кожен виклик: `repo.listMessages(session.id)` — усі повідомлення сесії (`packages/db/postgres-repo.ts:688-692`) → жорстке вікно **`.slice(-20)`** (`chat.ts:184`). Кожне повідомлення флатиться в текст: `text` + `summarizeCard(card)` (`chat.ts:21-47`) + статус `[ЗАСТОСОВАНО]`/`[НЕ ЗАСТОСОВАНО]` (`chat.ts:186-197`). При обрізанні спереду додається синтетична репліка «[раніше в цій розмові було ще N реплік…]» (`chat.ts:240-245`, QA5-05). **Сумаризації немає** — тільки rolling window 20.
- **recipe_gen**, **attachment_parse**: single-turn, історія не передається (`model.ts:308`, `:448`).
- **eval**: `conversation[]` фікстури мапиться 1:1 у messages (`model-client.ts:101-104`) — **без** slice(-20), без флатенінгу карток, без статусів, без маркера обрізання. Прод-шар формування історії евалом не тестується (розбіжність, див. розділ 7). Історії фікстур короткі (≤3 репліки).

## 4. Prompt caching

**Не використовується ніде.** Перевірено grep по всьому репо (без node_modules): `cache_control` — 0 збігів, `ephemeral` — 0 збігів.

Структурна причина: у всіх 4 місцях `system` передається **plain string** (`compose()` повертає string, `registry.ts:96`; `model.ts:188/296/414`; `model-client.ts:164`) — блокової форми, до якої чіпляється `cache_control`, немає.

При цьому проєкт про кешування знає:
- `03-prompts.md:7,22` — порядок блоків промпту свідомо «від найстабільнішого до найзміннішого» саме під префіксне кешування;
- `02-architecture.html:149` — контракт задекларовано як `usage: { input, output, cached }`;
- у БД і типах поле `cached` існує наскрізно (`model.ts:116`, `usage.ts:35`, `migrations/0003_token_usage.sql`), але завжди 0 (див. розділ 5).

Тобто: порядок блоків кешопридатний, контракт задизайнений — реалізації немає. Hit/miss-телеметрії, відповідно, теж немає.

## 5. Реальні usage-дані

### Прод-телеметрія: є, з прогалинами

Ланцюг: захоплення `resp.usage` у `model.ts:230/322/462` → `recordUsage` (`services/api/src/usage.ts:16-39`) → `repo.logTokenUsage` → **прямий SQL INSERT** у таблицю `token_usage` (`packages/db/postgres-repo.ts:591-604`; схема `migrations/0003_token_usage.sql`). Пишеться на кожен виклик, включно зі stub (`mode='stub'`, 0/0). Викликається з 5 місць: `chat.ts:123,260,376`, `attachments.ts:105`, `recipes.ts:78`.

**Gaps телеметрії:**
1. **`cached_tokens` завжди 0.** Колонка і параметр існують (`usage.ts:35`), але всі три місця захоплення читають лише `input_tokens`/`output_tokens` — `cache_read_input_tokens`/`cache_creation_input_tokens` з відповіді не читаються ніде (`model.ts:230/322/462`). Типи `RecipeCall.usage`/`AttachmentCall.usage` (`model.ts:240/340`) поля `cached` взагалі не мають.
2. **Агрегації немає.** Жодного SUM/GROUP BY по `token_usage`; єдиний рід `listTokenUsage` (`postgres-repo.ts:934-955`) не викликається з жодного HTTP-роуту — лише з тестів (`services/api/tests/usage.test.ts`). Дані пишуться, але ніде не читаються в проді: ні дешборда, ні квот, ні алертів.
3. **pino-нюанс — на повноту даних НЕ впливає:** запис у `token_usage` — прямий INSERT, він не проходить через логер, тож прод-рівень `warn` (`services/api/src/server.ts:38-42`) глушить лише видимість `req.log`-рядків, а не облік токенів.
4. **`promptVersion` не ідентифікує вміст промпту** (див. розділ 6, знахідка про ріст).
5. Снапшоти евалу не переносять `latencyMs` (рахується в `model-client.ts:198`, губиться в `runner.ts:48-64`), модель і агрегати — суми доводиться рахувати вручну.
6. **Ріст recipe-generator.md не верифікований у токенах:** git фіксує 4 224 → 8 721 chars (+4 497), але у `baseline.json` немає жодного recipe_gen-прогону (18 chat + 4 attachment_parse) — парного порівняння input, як для chat, зробити немає з чого.
7. `latest.json` перезаписується без збереження історії прогонів: вміст від 17:32 (31 прогін) о 20:59 замінено копією baseline (22 прогони) — дані прогону, на якому стоїть цей аудит, на диску вже відсутні (див. провенанс у таблиці нижче). Контекст прогону 17:32: це не автоматичний тригер, а ручний запуск з паралельної сесії калібрування промптів (card-rules.md, proposal-flow.md) — кожна ітерація такого калібрування в поточному вигляді системи вимагає повного прогону 30 фікстур через відсутність прапорця одиничного запуску, тобто сценарій з пункту 4 топ-списку підтверджений фактичним використанням, а не гіпотетичний.

## 6. Особлива увага: динаміка росту й QA/eval контур

### Ріст input +36% за один день — локалізовано у статиці

`baseline.json` (2026-08-30T13:30) → `latest.json` (17:32), **та сама promptVersion `2026-08-28`**: avg chat input 8 908 → 12 129.

Попарне порівняння **ідентичних** фікстур: усі 17 спільних chat-фікстур виросли рівномірно на **+3 188…+3 227 ток.** (фактично константа +3,2k), а всі 3 attachment_parse — **delta = 0**. Отже ріст не в даних фікстур і не в динамічній частині, а в спільному chat-префіксі.

Причина (робоче дерево vs HEAD): промпт-файли редагувалися «на місці» в межах тієї самої папки версії:
- `card-rules.md`: 27 046 → 32 158 chars (**+5 112**);
- `proposal-flow.md`: **новий файл 4 308 chars**, доданий у compose chat через manifest (у HEAD відсутній);
- разом +9 420 chars ≈ +3,2k ток. — збігається з поміряною дельтою;
- також `recipe-generator.md`: 4 224 → 8 721 (**+4 497**) — але, на відміну від card-rules/proposal-flow, вплив цього росту на реальні input-токени recipe_gen НЕ верифікований: у baseline немає recipe_gen-прогонів для парного порівняння (Gap №6).

Наслідок для телеметрії: `registry.ts:57-61` перевіряє лише `manifest.version === назва папки`, тож **`promptVersion` у `token_usage` і снапшотах не фіксує зміни вмісту промпту** — ріст на +3,2k ток./виклик пройшов під незмінним ідентифікатором.

### Лінійний ріст контексту комори

`serializePantry` (`packages/domain/context.ts:70-115`) — один рядок на кожну не-depleted партію, **без жодного обмеження кількості**; алерген/піст-мітки додають до ~150 chars на позицію (`context.ts:105,110`). Стосується і chat (режим 'none', `context.ts:218`), і recipe_gen (аліаси `p1..pN` самі по собі майже нічого не додають — лінійність від кількості партій та сама). Вхідні токени кожного виклику зростають пропорційно накопиченню даних користувачем із часом.

### QA/eval контур

- 31 фікстура (`packages/eval/fixtures/index.ts:40-131`; 1 скіп — `shelf-photo`, немає jpg і немає image-гілки, `model-client.ts:117`) → **30 послідовних викликів**, 1:1 фікстура-виклик, без ретраїв, без LLM-судді (інваріанти — чисті функції, `invariants.ts`).
- Фікстури дешеві (27 JSON разом 42 107 байт, медіана ~1,2 KB); дорогий — спільний префікс промпту. Розмір фікстури майже не впливає на вартість виклику.
- **Немає прапорця «прогнати одну фікстуру»** (`runner.ts:100-101` знає лише `--diff-only` і `--baseline`) — правка одного інваріанта чи однієї фікстури коштує повний прогін ~314k input.
- Між прогонами нічого не перевикористовується: снапшоти читаються лише для дифу (`runner.ts:37-41,160`), record/replay немає.
- Контекст МІЖ тестами повторно не пересилається (кожен виклик незалежний) — але саме тому 24 chat-виклики несуть 24 копії того самого префікса.

## Топ-5 підозрюваних джерел зайвого споживання

Ранжовано за орієнтовним впливом. Без запропонованих рішень (за правилом Фази 1).

1. **Ідентичний статичний префікс chat (~11,5k ток.) пересилається без кешування на кожному виклику** — і в проді (кожен хід чату), і в евалі, де він становить ~88% усього input прогону. `cache_control` відсутній у репо повністю; `system` скрізь рядок.

2. **`card-rules.md` — найбільший одиничний блок статики chat (32 158 chars = 74%), розмір якого при цьому не гарантовано стабільний і не версіонований:** той самий файл виріс на +5 112 chars за один день без зміни promptVersion (див. розділ 6).

3. **`serializePantry` — compounding per-user growth:** контекст комори росте лінійно і без обмеження з кількістю не-depleted партій (~150 chars/позиція з мітками), у chat і recipe_gen. Категорія відмінна від решти пунктів: це не одноразовий інцидент і не фіксований блок — вхідні токени кожного виклику зростають пропорційно реальному накопиченню даних користувачем із часом, тож вартість «повзе» без жодних змін коду чи промптів.

4. **Eval-ітерація без вибірковості:** будь-яка правка одного інваріанта/фікстури = повний прогін 30 викликів (~314k input, ≈$0,70), без прапорця одиничного запуску і без перевикористання результатів між прогонами. Сценарій підтверджений, не гіпотетичний: прогін 17:32, на якому стоїть цей аудит, — ручний запуск з паралельної сесії калібрування промптів, де кожна ітерація коштує повний прогін (Gap №7).

5. **Неверсіонований ріст промптів «на місці»:** +3,2k ток. на кожен chat-виклик за один день під незмінною promptVersion (card-rules +5,1 KB, новий proposal-flow +4,3 KB — вплив обох підтверджено парним порівнянням фікстур) — ріст невидимий для телеметрії, бо ідентифікатор версії не змінюється. Аналогічний ріст recipe-generator.md (+4,5 KB) зафіксований лише в git, у токенах не верифікований (Gap №6).
