# Задача: пройти Kitchen OS вручну через браузер і зафіксувати регресії

Це QA-сесія, а не розробка. Треба системно клацнути кожну кнопку в застосунку й записати:
- що працює як задумано
- що ламається (з крoком-репродукції + скріншотом)
- що плутає UX-но (без осуду — просто зафіксувати відчуття)

Цю задачу пише розробник, який жодного разу не клацнув застосунок у браузері після ~30 останніх коммітів. Всі test-suites зелені (63 vitest + 1 curl smoke), але UI-шляхи ніхто не пройшов рукою. Треба ти.

## Стан репо

Робоча гілка `main`, свіжий останній push. Гілка `catalog/expand` — паралельна робота іншого агента над каталогом, не чіпаєш.

## Setup — підняти локальний dev

```bash
# .env у корені має бути (перевірити перед стартом):
#   PG_URL=<Neon prod pooler URL>
#   PG_TEST_URL=<Neon dev branch pooler URL>
#   OPENROUTER_API_KEY=<real key>
#   APP_URL=http://localhost:5173

# Термінал 1 — API на :3000
pnpm --filter @kitchen/api start
# Побачиш: `api listening on :3000 (backend: postgres)`

# Термінал 2 — фронт на :5173
pnpm --filter @kitchen/web dev
# Побачиш Vite server ready

# Перевірка перед стартом
curl http://localhost:3000/health | jq
# Має повернути: {"ok":true,"prompt":"…","model_provider":"openrouter","attachments":"local_fs","mailer":"console","db":"ok"}
```

Якщо `db != "ok"` — Neon недоступний, перевірити VPN/PG_URL. Не продовжувати тестування, доки БД не буде живою.

## Тестові акаунти

Використай нові email-адреси щоразу як «створити новий акаунт». Наприклад: `qa-A@example.com`, `qa-B@example.com` — так БД лишається чистою і не заплутається з попередніми тестами.

Magic-link **не приходить на email** (мейлер stub = console). Треба:
- Дивитись stdout процесу API (термінал 1) — там буде `[mail] magic link → qa-A@example.com (діє 15 хв): http://localhost:5173/v1/auth/verify?token=...`
- Скопіювати URL, вставити в іншу вкладку

Не в'їхав як юзер? Дивись `services/api` термінал.

## Формат bug-report

Для кожного failure — окремий блок у файлі `qa-report.md` (створи в корені репо, не комітити):

```markdown
### [Область N] Короткий опис
**Кроки:**
1. …
2. …
**Очікував:** … 
**Отримав:** …
**Screenshot:** [ім'я файлу, збережи в /tmp/kos-qa-screenshots/]
**Console errors:** [copy-paste із DevTools]
**Network errors:** [4xx/5xx у Network tab]
**Severity:** blocker | major | minor | polish
```

Severity guide:
- **blocker** — юзер не може завершити основну дію (signin, apply, cook)
- **major** — фіча зламана або дає wrong result, але юзер може обійти
- **minor** — UI-баг, косметика, edge case
- **polish** — думки про UX, які варто зафіксувати

## Що НЕ робити

- **Не запускати `pnpm --filter @kitchen/db migrate`** — це проти prod-Neon, не треба.
- **Не комітити нічого** — QA-сесія тільки для звіту. Файл `qa-report.md` не в git.
- **Не міняти .env** — вже налаштоване.
- **Не запускати smoke script** (`pnpm smoke`) — вбʼє існуючий API.
- **Не робити destructive-операції** проти prod Neon (drop, truncate, ручні DELETE).
- **Не витрачати токенів OpenRouter** без потреби — recipe generation дорогий, ~$0.01 за виклик. Тестуй кожен recipe раз, не 5.
- **Не логінься чужим email** — використовуй тільки `qa-*@example.com` варіанти.
- **Не публікуй скріншоти нікуди** — тільки локально.

## Deliverable

`qa-report.md` у корені репо (untracked) із:
1. **Підсумок** — «X з 27 перевірок пройшли, Y провалів (Z blocker, W major, ...)»
2. **По одному блоку на кожен провал** (формат вище)
3. **Загальні відчуття про UX** — 5-10 речень «як воно почувається», хто б купив, чого не вистачає з поверхні.

Коли готово — постав файл у корінь, кажи розробнику, і зупиняйся. Він переглядає, вирішує що фіксити першим.

## Обмеження часу

Раціональний обсяг: 90-120 хвилин. Якщо якась область вимагає більше — пропускай і фіксуй у звіті як «не встиг перевірити». Не витрачай день на один edge case.
