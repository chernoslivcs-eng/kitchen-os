# Задача: розширити каталог із 131 позиції до 1500–2500

Це data-робота, яка не поміщається в звичайну сесію чату. Потрібна окрема довга сесія — краще Claude Code Ultra або Cowork із доступом до браузера й запуском кількох агентів паралельно.

## Що зробити коротко

`packages/catalog/seed.ts` містить 131 інгредієнт. Розширити до **1500–2500 позицій** із каноничними назвами, аліасами українською й латиницею, ієрархічними категоріями (`мідії → молюски → морепродукти → тваринне`), правильними алергенними групами і зонами зберігання. Джерела: каталог мереж (Сільпо, АТБ, Метро), USDA для поживності, відкриті бази продуктів. Все зафіксувати в тому ж форматі, що поточні 131 позиції, і провести через існуючі тести.

## Чому це важливо

Каталог — не «оптимізація», а умова коректності. Без нього **чотири різні механізми лікуються милицями**:

- **Алергени за змістом.** Алергія «молюски» не помічає «мʼясо мідій», бо збіг за рядком не бачить зв'язку. Каталог з `allergen_groups: ['молюски', 'морепродукти']` на позиції «мʼясо мідій» це закриває.
- **Релігійні обмеження.** «Не їм свинину» не ловить «Ковбаса Міланська», якщо в її категоріях немає `свинина`.
- **Синоніми в резолвері.** «Курячий бульйон» не знаходить «фонд курячий» без alias-таблиці.
- **Морфологія в пошуку.** «Кінзу» не знаходить «кінза» без відмінкових форм у `aliases`.

Три цих критерії вже перевіряють тести в `packages/catalog/tests/{allergen,antipattern,search}.test.ts` — 18 тестів, усі мають лишитись зеленими після розширення.

## Умова готовності

- `packages/catalog/seed.ts` містить **1500-2500 позицій**
- `pnpm --filter @kitchen/catalog test` → 18/18 ✓
- Немає дублікатів `key`
- Немає колізій алісів між позиціями (той самий alias не веде в дві різні позиції)
- `allergen_groups` кожної позиції звірене з реальним складом (не «здогадка агента»)
- `categories` — коректна ієрархія від конкретного до загального
- Українські відмінкові форми в `aliases` для позицій, які часто зустрічаються в мовленні
- Латинські аліаси для брендованих продуктів (`spaghetti`, `mozzarella`, `parmigiano reggiano`)

## Схема

Кожна позиція — обʼєкт із інтерфейсом (`packages/catalog/seed.ts` рядок 8):

```ts
export interface CatalogItem {
  key: string;                                                    // snake_case, унікальний
  name: string;                                                   // канонічна українська назва
  aliases: string[];                                              // як зустрічається в чеках і мовленні
  categories: string[];                                           // ієрархія від конкретного до загального
  allergen_groups: string[];                                      // «молюски», «горіхи», «глютен», «молочне»
  zone_default: 'dry' | 'fridge' | 'freezer' | 'fresh' | 'spices' | 'drinks';
  unit_weight?: number;                                           // вага «однієї штуки», якщо продукт поштучний
  density?: number;                                               // g/ml для рідин
  nutrition?: { kcal: number; p: number; f: number; c: number }; // на 100 г
}
```

Приклади з існуючих 131:

```ts

```

## Пропоную такий підхід — паралельні агенти з валідацією

Не робити одним великим агентом «згенеруй мені 2000 продуктів» — вихід буде непослідовним і з галюцинаціями. Замість цього:

**Фаза 1: паралельне генерування по категоріях.**

- 10–15 агентів запускаються паралельно, кожен на 1–3 категорії з таблиці вище
- Кожен агент отримує вхід: специфікацію `CatalogItem`, приклади з існуючих 131, посилання на джерела (silpo.ua/catalog, atb.market/catalog, metro.ua, USDA FoodData Central)
- Вихід: масив `CatalogItem` з ~100–200 позиціями по категорії
- Формат виходу: TypeScript-масив, готовий до вставки в seed.ts

Приклад prompt-а для агента:

> Ти генеруєш каталог інгредієнтів категорії «М'ясо, птиця, ковбаси» для українського домашнього продукту. Формат — `CatalogItem` (див. схему нижче). Треба ~150 позицій. Аліаси мають включати відмінкові форми українською для того, що часто в чеках («курка», «курки», «курча»), брендові варіанти («Наша Ряба», «Гаврилівські курчата»), латиницю для міжнародних сортів («salami», «prosciutto»). Категорії йдуть від конкретного до загального: «Ковбаса Міланська» → `[ковбаса, сирокопчене, свинина, м'ясо, тваринне]`. Allergen_groups: заповнюй ТІЛЬКИ якщо в тебе є конкретне джерело (склад на упаковці або авторитетне посилання) — не «вгадуй». Джерело — silpo.ua/catalog/gastronomy, метро.ua. Формат виходу — валідний TypeScript-масив.

**Фаза 2: валідатор алергенів.**

- Окремий агент (або 3–5 паралельно по чанках) читає вихід фази 1
- Для кожної позиції з непорожнім `allergen_groups` перевіряє реальний склад:
  - Пошук по офіційним ресурсам виробника
  - Порівняння з посилальним списком (наприклад, класичний рецепт песто містить кедрові горіхи → `allergen_groups: ['горіхи']` виправдане)
  - Кимчі, соєві соуси й багато що з ферментованого міститимуть рибний соус — треба перевіряти конкретний бренд
- Вихід: список змін (додати/прибрати `allergen_group`), лог з обґрунтуванням

**Фаза 3: збирач.**

- Один агент (не паралельно) читає всі виходи фаз 1 і 2
- Обʼєднує, ловить конфлікти:
  - Дублікати `key` → перейменовує другий, або зливає, якщо це те саме
  - Аліас, що веде в дві позиції → уточнює
  - Категорії, що суперечать (позиція «сир» без `молочне` → додає)
- Записує фінальний масив у `packages/catalog/seed.ts`, зберігаючи 131 стартову позицію на початку файлу

**Фаза 4: тести й ручна вибірка.**

- `pnpm --filter @kitchen/catalog test` → 18/18
- Написати додатково: тест на відсутність дублікатів `key`, тест на «жоден `alias` не веде в дві позиції»
- Ручна вибірка 20-30 позицій із різних категорій — переглянути очима людини

## Чого агенти не мають робити

- **Не вгадувати алергени** без джерела. Порожній `allergen_groups: []` кращий за «здогадався, бо кимчі часто містять рибний соус — напишу»
- **Не переносити 131 стартову позицію** — вони перевірені й пройшли критерії, лишити як є
- **Не редагувати `logic.ts`** — це стабільна логіка збігу, зміни в неї — окрема задача
- **Не міняти інтерфейс `CatalogItem`** — тоді треба міграція
- **Не додавати неукраїнські інгредієнти без причини** — Kitchen OS цільово для української кухні; глобальний ринок — наступний етап
- **Не додавати неактуальне** — «мамалига з насінням чіа» не потрібна, потрібне те, що реально купують

## Обмеження — прочитати, перш ніж почати

- **Обсяг агента-генератора має бути обмежений 1-3 категоріями на пасаж.** Один агент на всі 2000 — гарантована галюцинація на середині.
- **Токен-ліміт** реальний: якщо категорія масивна (спеції, напої) — розбити на підкатегорії (окремо «індійські спеції», «європейські трави», «українські сушені»).
- **Валідатор має право видалити позицію.** Якщо не може підтвердити реальність продукту в українських мережах — краще без нього.

## Що робити з результатом

Після фази 3:
1. Комітнути `packages/catalog/seed.ts` окремо: `chore(catalog): expand from 131 to N positions`
2. Написати підсумок у commit-body:
   - Скільки позицій зʼявилось у кожній категорії
   - Скільки алергенів верифіковано, скільки залишилось з `[]`
   - Джерела, які використовували
3. Оновити `packages/catalog/README.md` — цифру «16 позицій» на нову
4. Прогнати `pnpm test`, показати результат в чат
5. Опційно: створити `catalog/allergen-audit.md` з таблицею «продукт → джерело складу → allergen_groups» на верифікованих позиціях. Юзеру знадобиться це для юридичного покриття, коли алергії стануть чутливими даними в проді.

## Правила безпеки для агентів

- **Приватність.** Каталог не містить персональних даних, публічний. Але описи скіпати, якщо вони копіюють текст з мереж дослівно — це може порушити копірайт. Аліас «моцарела» — ок, скопійований опис продукту з silpo.ua — ні.
- **Не змінювати `.env`** — це секретний файл, він у `.gitignore`.
- **Не пушити** до `main`, поки тести не зелені й не пройшла ручна вибірка. Якщо агенти самі роблять коміти — тільки в feature-гілку `catalog/expand`.
- **Не робити ресет міграцій, паролю Neon, drop table** — жодні destructive operations на існуючих даних.
