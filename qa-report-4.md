# QA-4 — пам'ять, складні обмеження, складні рецепти

Прогін: 2026-08-29, ~19:00–20:20. Акаунт `chernosliv.cs@gmail.com`, локальний стек
(web :5173 + api :3000), prompt `2026-08-28`, chat = `anthropic/claude-haiku-4.5`,
recipe_gen = `anthropic/claude-sonnet-4.5`.

**Чистий акаунт знову недоступний.** Magic-link іде тільки в stdout API, а мій shell на
твоїй машині сидить у sandbox із `--unshare-net` і `--die-with-parent` — ані підняти
власний API з редиректом логу, ані дотягнутися до stdout наявного я не можу. Обхід із
брифу перевірив і він структурно неможливий. Онбординг `stage=1` не бачено за жоден
із чотирьох прогонів.

**Метод.** Браузер для рендеру (`/r/:id`, історія), прямі виклики API з вкладки для
чату й карток. Два cook-run-и створені через `POST /v1/cook-runs` — той самий виклик,
що робить кнопка «Готове» в Cook Mode; UI-шлях Cook Mode вже перевірений у QA-1/2.
Причини всіх знахідок підтверджені в коді.

## Головне

Три блокери. Два з них — це один і той самий структурний факт із двох боків: **модель
не бачить нічого, окрім системного промпту, комори, cook-run-ів і однієї поточної
репліки.** Ані історії розмови, ані профілю.

Це переписує висновок QA-3. QA3-05 («невизначений намір → петля уточнень») я тоді
назвав промптовою проблемою. Це не промпт. Модель фізично не може отримати відповідь
на своє ж уточнення.

## Блокери

### QA4-01 — чат без історії розмови

`services/api/src/model.ts:165`

```ts
messages: [{ role: 'user', content: args.text }],
```

`args.session_id` оголошено в `ChatArgs` (model.ts:83) і **не використано жодного разу**.
Повідомлення пишуться в БД (`repo.saveMessage`), UI їх відтворює після F5 — але в модель
вони не йдуть.

Відтворення (одна сесія, послідовно):

| # | я | модель | картка |
|---|---|---|---|
| 1 | Що приготувати на вечерю? | «У тебе є лосось — показати варіанти з ним, чи щось інше?» | — |
| 2 | Так, з лососем | «Про лосось на пательні з лимоном, який вийшов ідеально? Дай рецепт чи готуємо знову?» | — |
| 3 | Готуємо знову | «Лосось на пательні з лимоном — той, що вийшов ідеально? Або спробуємо щось інше?» | — |
| 4 | А може запекти в духовці з травами? | «Ти це вже робив вчора — вийшло пересолено й сухо…» | — |
| 5 | Так, робимо так само. Дай рецепт. | «Лосось на пательні з лимоном — той, що вчора вийшов ідеально?» | — |

П'ять реплік, нуль карток, те саме питання тричі. На кроці 5 людина каже «так, робимо
так само, дай рецепт» — і отримує те питання, на яке вже двічі відповіла.

В окремій сесії: `«Дай мені рецепт лосося на пательні. Без питань, просто рецепт»` →
модель дає рецепт **прозою в бульбашці**, без `proposal`-картки. Далі `«Так»` →
**«Привіт! Я — твій кухар. Що готуємо?»**. Вітання посеред розмови — бо для моделі це
і є перша репліка.

**Фікс.** `chat.ts` вже має `repo.listMessages(session.id)` (використовується в
`session.ts:19`). Додати в `ChatArgs` і прокинути:

```ts
// routes/chat.ts, перед callChat
const history = (await repo.listMessages(session.id))
  .slice(-20, -1)                       // без щойно збереженої user-репліки
  .filter((m) => m.text)
  .map((m) => ({ role: m.role, content: m.text! }));

const call = await callChat({ user_id, session_id: session.id, text: text ?? '', pantry, stage, recentCookRuns, history });
```

```ts
// model.ts
export interface ChatArgs {
  ...
  history?: { role: 'user' | 'assistant'; content: string }[];
}

// у callChat:
messages: [...(args.history ?? []), { role: 'user', content: args.text }],
```

Ліміт у 20 реплік — щоб не рознесло вхідні токени (зараз системний блок і так 5 920).
Картки в історію не кладемо: модель має бачити текст розмови, не JSON.

### QA4-02 — профіль ніколи не потрапляє в модель

`services/api/src/routes/chat.ts:101` читає `repo.getProfile(user_id)` **виключно** щоб
порахувати `stage`. `callChat` (model.ts:156-160) склеює системний промпт із
`[КОМОРА]` і `[ОСТАННІ ГОТУВАННЯ]` — блоку профілю немає. `callRecipe` (model.ts:258)
профіль не приймає взагалі. `compose()` у `packages/prompts` профіль не знає.

Тобто алергії, wishes і antipatterns зберігаються, показуються в UI — і не впливають
ні на що.

**Емпірично.** Записав і застосував алергії: `арахіс, волоські горіхи, мигдаль, кешʼю`
(`GET /v1/profile` підтверджує). Нова сесія, `«Хочу щось солодке до чаю з того, що є вдома»`:

```json
{"type":"proposal","items":[
  {"title":"Булочка з корицею", "...": "..."},
  {"title":"Шоколад молочний","desc":"З мигдалем або с семінням чіа — перекусити дольку-дві…"}]}
```

Далі `«Можна шоколад?»` → «Є два варіанти — **мигдальний** з какао або з чіа».

Людині із зафіксованою алергією на мигдаль продукт двічі пропонує мигдаль. Це не
косметика — це те, заради чого профіль існує.

**Фікс.**

```ts
// model.ts
function serializeProfile(p: Profile | null): string {
  if (!p) return '';
  const parts: string[] = [];
  if (p.allergies.length)    parts.push('АЛЕРГІЇ (тверда межа, ніколи не пропонувати): ' + p.allergies.join(', '));
  if (p.antipatterns.length) parts.push('НЕ ЛЮБИТЬ: ' + p.antipatterns.join(', '));
  if (p.wishes.length)       parts.push('ЛЮБИТЬ: ' + p.wishes.join(', '));
  const eq = Object.keys(p.equipment ?? {});
  if (eq.length)             parts.push('ТЕХНІКА: ' + eq.join(', '));
  return parts.length ? '\n\n[ПРОФІЛЬ]\n' + parts.join('\n') : '';
}
```

Підключити в обох місцях — `callChat` (додати `profile` в `ChatArgs`, `chat.ts` уже має
об'єкт у руках) і `callRecipe` (`recipes.ts:43` поруч із `listBatches`). У
`packages/prompts/versions/*/card-rules.md` додати правило: *«АЛЕРГІЇ — тверда межа.
Ніколи не пропонуй страву чи інгредієнт зі списку, навіть якщо він є в коморі. Якщо
людина просить саме його — скажи про алергію і запитай, чи знімати її з профілю.»*

Без цього правила модель отримає список і все одно може ним знехтувати.

### QA4-03 — генератор рецептів повертає неіснуюче поле `q`, комора списується повністю

Схема (`model.ts:174`): `RecipeIng { p?, n?, v?: number, u?: string }`.
Промпт `recipe-generator.md` описує JSON так:

```
"ing":[…]
```

Три крапки. Схеми інгредієнта в промпті **немає взагалі** — модель її щоразу вигадує.

Два рецепти, дві різні вигадані форми, жодного `v`:

```json
// «Лосось на пательні з лимоном»
[{"p":"a1d2…","q":"400g"},{"n":"лимон","q":"1шт"},{"n":"олія","q":"2ст.л"}]
// «Паста карбонара»
[{"n":"спагеті","q":320,"u":"г"},{"n":"сіль","q":0,"u":""}]
```

**Наслідок 1 — комора.** `cook-runs.ts:normalizeForBatch(ing.v, ing.u, batch.unit)` отримує
`undefined, undefined` → повертає `null` → код іде в гілку **повного** `deplete`, а не
`subtract`. Перевірив на живому: рецепт бере 400 г із партії на 400 г, у `changes`
записано `{"op":"deplete"}`. Для лосося різниці немає, для пляшки олії й «2 ст.л» —
зникне вся пляшка.

**Наслідок 2 — UI.** `Recipe.tsx:123` і `SharedRecipe.tsx:94` рендерять `ing.v && ing.u`.
На `/r/1a02dea8…` список інгредієнтів такий: `Лосось · лимон · олія · сіль · перець` —
**без жодної кількості**. Спільний рецепт непридатний до готування.

**Фікс** — замінити три крапки на справжню схему в `recipe-generator.md`:

```
"ing":[{"p":"uuid партії з комори"},{"n":"назва","v":400,"u":"g"}]
```

і додати в «Ключові правила»:

- `v` — **число**, `u` — одне з `g`, `ml`, `pcs`, `pack`. Ніяких інших полів і ніяких
  рядків на кшталт `"400g"`. Кількість «за смаком» — просто без `v` і `u`

Плюс страховка на бекенді, бо промпт — це не контракт. У `recipes.ts` після
`callRecipe`, перед `return`:

```ts
const bad = call.recipe.ing.filter((i) => 'q' in (i as object) || (i.v != null && typeof i.v !== 'number'));
if (bad.length) req.log.warn({ bad }, 'recipe-ing-schema-violation');
```

І в `cook-runs.ts` не депляцувати всю партію, коли кількість невідома, а тільки
позначати `opened` — тихе знищення партії гірше за недосписання.

## Major

### QA4-04 — undo профільної картки псує профіль (аліасинг об'єкта)

`packages/domain/apply.ts:118-124`

```ts
const before = await repo.getProfile(actor_user_id);
const snapshot: UndoSnapshot = { kind: 'profile', before: { profile_before: before ?? undefined } };
const next: Profile = before ? { ...before } : { … };
```

`{ ...before }` — поверхнева копія. `next.allergies` — **той самий масив**, що
`before.allergies`. Далі `applyProfileOp` робить `list.push(label)` і мутує масив, на
який дивиться знімок. Тобто `profile_before` фіксує стан **після** зміни.

Перевірив: застосував картку з 4 алергіями, потім ще три картки, потім натиснув undo
на найпершій. Результат — алергії лишились на місці (знімок їх уже містив), а `wishes`
і `antipatterns`, додані пізніше, **стерлися**. Тобто undo старої картки не відкочує
свою зміну і при цьому знищує всі наступні.

**Фікс** — глибока копія в момент знімка:

```ts
const snapshot: UndoSnapshot = { kind: 'profile', before: { profile_before: before ? {
  ...before,
  allergies: [...before.allergies],
  wishes: [...before.wishes],
  antipatterns: [...before.antipatterns],
  equipment: { ...before.equipment },
} : undefined } };
```

Окремо: `undoCard` (apply.ts:347) робить `upsertProfile(profile_before)` — повну заміну
документа. Навіть із правильним знімком undo картки №1 затре картку №2. Для MVP
прийнятно, але це треба знати; правильне рішення — оп-левел undo (інвертувати
`applied_ops`), а не rollback документа.

### QA4-05 — `kind: 'member'` і `'note'` тихо губляться, а API рапортує успіх

`apply.ts:313`: `// note / member — MVP ігнорує`.

`ProfileKind` (types.ts:67) містить `member`, промпт дозволяє його генерувати, модель
його генерує. `«Моя дружина вегетаріанка, готуємо на двох»` →
`{"op":"add","kind":"member","label":"дружина","diet":"vegetarian"}`, apply повертає
**`{"applied": 1}`**, UI показує успіх — а в профілі нічого немає.

Це гірше за відмову: людина вважає, що продукт знає про вегетаріанку в домі.

**Фікс** — рахувати те, що справді лягло:

```ts
let landed = 0;
for (const idx of chosen) {
  const op = card.ops[idx];
  if (!op) continue;
  if (applyProfileOp(next, op)) landed++;      // повертати boolean
}
…
return { applied: landed, undo_token, already: false };
```

І в `card-rules.md` заборонити `member`/`note`, доки немає таблиць — щоб модель не
обіцяла людині того, чого продукт не вміє.

### QA4-06 — складний рецептний запит падає в 502

`POST /v1/recipes/generate` з `«Святкова вечеря на 6 осіб: лосось, гарнір і десерт»` →
`502 {"error":"model_returned_no_recipe"}`. Модель відповіла прозою, і відповідь
розумна: *«400 г лосося — це мало на шістьох…»*. Її викидають, лишається 400 символів
у полі `raw` для дебагу.

Людина бачить помилку там, де модель насправді правильно сказала, що завдання
неоднозначне.

**Фікс** — повернути це як діалог, а не як 502:

```ts
if (!call.recipe) {
  return reply.code(200).send({ recipe: null, reply: call.raw.slice(0, 600), meta: call.meta });
}
```

і на клієнті показати `reply` як репліку кухаря з кнопкою «уточнити». Плюс правило в
`recipe-generator.md`: *«Один рецепт за раз. Якщо просять меню з кількох страв — обери
головну, згенеруй її, а решту назви в `op`.»*

### QA4-07 — конфлікт wish ↔ anti не ловиться

`«Не люблю кінзу»` → `anti: кінза` ✓. Далі `«Дуже люблю кінзу, додавай її скрізь»` →
`wish: «кінза в усе»`, без жодної згадки про суперечність. У профілі опиняється
`wishes: ["кінза в усе"]` і `antipatterns: ["кінза"]` одночасно.

Це наслідок QA4-02 — модель не бачить профілю, тому не має з чим порівнювати. Після
фіксу QA4-02 треба додати правило в `card-rules.md`: *«Якщо нове побажання суперечить
тому, що вже в профілі — не пиши картку мовчки. Назви суперечність і спитай, що лишаємо.»*

### QA4-08 — `0дн тому` перетворюється на «вчора»

`model.ts:99` `serializeCookRun`:

```ts
const days = Math.round((Date.now() - new Date(r.finished_at).getTime()) / 86_400_000);
const parts = [r.title, `${days}дн тому`];
```

Готування 20 хвилин тому серіалізується як `0дн тому`. Модель двічі сказала
**«Ти це вже робив вчора»** і **«той, що вчора вийшов ідеально»**. Продукт бреше про
факт із життя людини — дрібниця, яка руйнує довіру до пам'яті сильніше, ніж її
відсутність.

**Фікс:**

```ts
const ms = Date.now() - new Date(r.finished_at).getTime();
const days = Math.floor(ms / 86_400_000);
const when = days === 0 ? 'сьогодні' : days === 1 ? 'вчора' : `${days} дн тому`;
const parts = [r.title, when];
```

## Minor

- **Рецепт у чаті приходить прозою.** Коли модель усе ж дає рецепт у відповідь на прямий
  запит, вона пише його текстом у бульбашці, без `proposal`-картки. Наслідок: немає
  Cook Mode, немає таймерів, немає списання комори, немає `/r/:id`. Це той самий
  контракт карток, який тримає весь продукт — і він тут просто не спрацьовує. Після
  фіксу QA4-01 перевірити ще раз: підозрюю, що частина промахів була через те, що
  модель «застрягала» в уточненнях.
- **Історія чатів нерозрізненна.** `Feed.tsx:399` підписує сесії лише `дата · час ·
  N повідомлень`. За сьогодні їх шість, усі «Сьогодні · 19:xx». `SessionRow.title` існує
  в типі й ніде не заповнюється. Найдешевше — писати туди перші 40 символів першої
  user-репліки при створенні другого повідомлення.
- **Порожній стан історії бреше.** «Тут порожньо. Кожна сесія зберігається — вона
  зʼявиться тут завтра» (`Feed.tsx:396`) — насправді сесія зʼявляється одразу, фільтр
  `message_count > 0`.
- **Комора: ціна з чека потрапила в кількість.** `Шоколад 25 Мол ЛТ Kor Мигдал Кок ·
  59.99pcs`, `Багет 160 Подов Гречм Мін · 32.99pcs`. 59.99 — це гривні, не штуки.
  Модель це бачить і будує на цьому репліки («25 грамів, молочний»). Проблема ingest-у
  чека, не чату, але вона отруює весь контекст.
- **Дублі в коморі.** Кожна позиція присутня двічі з різними id — схоже, один чек
  застосований двічі. Варто перевірити ідемпотентність apply для `intake_diff`.

## Що лишилось у твоєму акаунті

Прибрав: комора назад до 20 позицій (лосось видалено), профіль порожній, рейтинги й
verdict-и тестових готувань обнулено, cook-run зі списанням лосося відкочено.

Лишилось і прибрати не можу — **три рядки в історії готувань** («Лосось на пательні з
лимоном» ×2, «Лосось у духовці з травами»), бо ендпоінта на видалення cook-run немає.
Вони без рейтингу й verdict-у, тож на поведінку моделі майже не впливають. Плюс кілька
порожніх сесій у «⌚ Історія» за сьогодні.
