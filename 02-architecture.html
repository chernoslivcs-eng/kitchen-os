Архітектура · продакшн

Що будувати після прототипу. Прототип — фронтенд без бекенду, з викликами моделі напряму з браузера. У продакшні між ними стає сервер, і це змінює три речі: де живуть ключі, де живе стан і хто платить за токени.

01 · Межі

Що переїжджає на бекенд і чому

ЩоУ прототипіУ продакшніЧому

Що лишається на клієнті: рендер карток, черга вкладень, таймери Cook Mode, оптимістичні оновлення. Усе, що має працювати при поганому звʼязку біля плити.

03 · Каталог

Деталь, якої немає, і без якої не працюють чотири речі

У прототипі все тримається на збігу рядків. Це виходить боком у чотирьох різних місцях, і кожне лікується окремою милицею.

Де болитьПрикладЩо дає каталог
Алергени за змістомалергія «молюски» не помічає «мʼясо мідій»allergen_groups на позиції каталогу
Релігійні обмеження«не їм свинину» не ловить «ковбаса Міланська»категорії: [мʼясо, свинина, ковбаса]
Синоніми в резолвері«курячий бульйон» не знаходить «фонд курячий»aliases
Морфологія в пошуку«кінзу» не знаходить «кінза»лематизація на індексі
Це найдорожча відсутня деталь у продукті. Обсяг для першої версії — 1500–2500 позицій із категоріями й аліасами українською. Джерела: відкриті бази продуктів, каталоги мереж, USDA для поживності. Заповнюється один раз і далі поповнюється з реальних чеків.
04 · Сервіси

Розкладка бекенду

chat-service

Збирає промпт, викликає модель, валідує відповідь, застосовує побічні ефекти після підтвердження. Тримає ліміти й облік токенів на користувача.

pantry-service

Партії, стани, терміни, кошик закінченого, авторство. Єдине джерело правди про комору.

catalog-service

Резолвер, синоніми, категорії, алергенні групи, поживність. Читається всіма.

intake-service

Вкладення: зображення, PDF, текст. Стиснення, зберігання, розбір, дедуплікація між кількома фото.

retail-service

OAuth із мережею, MCP-виклики, мапінг наш список ↔ їхній каталог, імпорт чеків.

calendar-service

Сезони, пасхалія, місячні дати. Розпізнавання традиції з побажань. Горизонт — рік.

Головний ендпоінт

POST /v1/chat
  { session_id, text, attachments[], audience[] }
  →
  { reply, card, usage: { input, output, cached }, mode }

Побічних ефектів НЕ застосовує. Картка повертається як пропозиція.

POST /v1/cards/:id/apply
  { selected: [op_index] }
  →
  { applied, undo_token }

POST /v1/cards/:id/undo
  { undo_token }
Розділення «повернути картку» і «застосувати» — не формальність. Це те саме правило, що й у прототипі: модель ніколи не пише в стан напряму. На бекенді воно стає ще важливішим, бо застосування має бути ідемпотентним і мати токен скасування.
05 · Виклики моделі

Профілі, кешування, ліміти

ВикликПрофільВхідКешується
chat / пропозиціїfast≈4300роль + правила + комора
генерація рецептаsmart≈3200роль + правила
розбір вкладеньfast, temperature 0≈2500 + зображенняроль + комора
добір кроківfast≈300—
пошук у коморіfast≈2500комора
Кешування: префікс = роль + правила карток + комора.
Він змінюється рідко, а решта промпту — часто. Тому порядок блоків
у системному промпті має бути СТАЛИЙ, від найстабільнішого до найзміннішого:

  ROLE → правила карток → комора → профіль → адресати → приводи → досвід

Переставили місцями — кеш зламався.
Контрінтуїтивне, перевірене розрахунком: годинний TTL кешу дорожчий за пʼятихвилинний при типовій сесії з трьох викликів. Запис коштує вдвічі, а читань замало, щоб окупити. Довгий TTL має сенс лише для користувачів із довгими сесіями — тобто це параметр, який треба міряти, а не задавати наперед.
Спільна комора × кілька учасників = множення рахунку. Двоє людей у домі отримують той самий стан комори в промпті двічі, і кешування не рятує, бо сесії різні. Варіанти: спільний кеш-префікс на рівні дому, або віддавати комору інструментом за запитом замість того, щоб класти в кожен промпт.
06 · Інтеграція з мережею

MCP «Сільпо»

URL        https://mcp.silpo.ua/mcp
Транспорт  Streamable HTTP
Авторизація OAuth 2.1 + PKCE
Токен      ТІЛЬКИ серверно (вимога документації)

Сценарій «список → кошик»:
  get_my_shopping_cart → get_shopping_cart_by_id → get_time_slots
  → find_products_batch (до 30 позицій) → add_or_update_cart_products
  → посилання на оформлення

Сценарій «чеки → комора»:
  get_my_offline_orders → IntakeDiff з confidence 1, evidence receipt_line

Профіль:
  get_my_food_restrictions, get_my_family
Структуровані дані знімають цілий пласт евристики. Позиція з чека мережі приходить із повною впевненістю. Порівняйте з фото, де ми боремося за 60% і вигадані сорти. Резолвер лишається потрібним для того, чого в мережі немає.
Проєктувати треба під кілька мереж. Інтерфейс RetailProvider із чотирма методами: findBatch, addToCart, receipts, restrictions. Сільпо — перша реалізація, не єдина. Універсальний запасний канал для всіх мереж — QR фіскального чека через реєстр ДПС.
07 · Клієнт

Що переносити з прототипу як є

Переносити

  • Три компоненти карток: список зі scope, пропозиція, рецепт
  • Один канал уточнення через префікс у полі вводу
  • Черга вкладень до відправки
  • Cook Mode із згортанням і збереженим кроком
  • Скасування останньої зміни комори
  • Швидкий локальний ввід «+ молоко 1 л» — працює без мережі

Переробити

  • 51 стан у головному компоненті → стор із доменними зрізами
  • Оптимістичні оновлення з відкотом при помилці сервера
  • Офлайн-черга: дії в Cook Mode мають доїжджати після відновлення звʼязку
  • Зображення: завантаження окремим запитом, а не в тілі повідомлення
  • Стрімінг відповіді — зараз чекаємо повний JSON
Найважливіше з клієнтського: Cook Mode має працювати при поганому звʼязку. Людина стоїть біля плити, таймер іде, і «немає інтернету» тут неприйнятне. Кроки й таймери — локально, списання — у чергу.
08 · Приватність

Межа проходить за природою даних

СПІЛЬНЕ (household_id)     комора, обладнання, список, календар дому
ОСОБИСТЕ (user_id)         профіль, досвід, журнал, сесії, задуми
З ОПЦІЄЮ ПОДІЛИТИСЬ        окремий рецепт, окрема нотатка

Сесії не шеряться НІКОЛИ — це щоденник, а не документ.
Задуми успадковують приватність сесій, з яких виведені.
Пріоритет власника. Асистент готує для того, хто питає. Обмеження інших учасників підключаються тільки коли їх названо адресатами — ні мовчки, ні «про всяк випадок».
Що треба вирішити юридично: алергії й релігійні обмеження — чутливі персональні дані. Зберігання, експорт, видалення й термін життя мають бути описані до першого користувача, а не після.
