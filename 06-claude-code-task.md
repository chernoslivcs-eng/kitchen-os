# Завдання для Claude Code

## Що це

Застосунок, який веде домашню комору й готує разом із людиною. Є робочий прототип — один файл на 6400 рядків, React, виклики моделі напряму з браузера. Треба перенести його в продакшн: фронтенд + бекенд + база + інтеграції.

Пакет документів лежить поруч:

- `01-product.html` — продуктова архітектура: зони, модулі, картки, принципи
- `02-architecture.html` — схема даних, сервіси, API, кешування
- `03-prompts.md` — промпти дослівно + реєстр збоїв
- `04-roadmap.html` — етапи й залежності
- `05-risks.html` — ризики й відкриті питання
- `kitchen-prototype.jsx` — робочий прототип

**Прочитай `01` і `02` перед тим, як писати код.** У прототипі коментарі пояснюють причини рішень, не тільки що робить код. Ці причини важливіші за сам код: він писався швидко й місцями криво, а рішення оплачені помилками.

---

## Три правила, які не можна порушувати

**Модель ніколи не пише в стан напряму.** Будь-яка зміна комори, списку чи профілю проходить через картку з підтвердженням людини. На бекенді це `/v1/chat` повертає картку, `/v1/cards/:id/apply` застосовує. Не об'єднувати.

**Модель показує пальцем, а не називає.** Рецепт посилається на партію в коморі через id (`{"p":"p12"}`), а не через назву. Зіставлення рядків — запасний шлях. Порушення цього правила ламає всю точність.

**Інформація — репліка, дія — інтерфейс.** Якщо від людини нічого не потрібно, це говориться словами в потрібний момент, а не висить постійним блоком. Не додавати плашки під те, що система просто знає.

## Порядок

### Крок 0 — інфраструктура перевірки

**Це робиться першим, до будь-якої фічі.**

Набір зафіксованих кейсів і скрипт, який проганяє їх після кожної зміни промпту:

```
fixtures/
  receipt-abbreviated.txt      чек зі скороченнями: «СИР КАМБОЦ.70% 193Г»
  receipt-nonfood.txt          чек із побутовим і напоями
  shelf-photo.jpg              фото полиці з неоднозначними продуктами
  recipe-freeform.txt          вставлений рецепт без кількостей
  topic-continuity.json        діалог: обговорення страви → «дай рецепт»
  missing-ingredient.json      запит про страву з відсутнім продуктом
  allergen-conflict.json       рецепт з алергеном при названому адресаті
```

Для кожного — очікуваний **інваріант**, не точний текст:

- чек: розпізнано ≥80% рядків, скорочення розгорнуті, ціни проігноровані
- «дай рецепт»: назва страви збігається з обговорюваною
- відсутній продукт: повернуто `proposal`, а не відмова
- алерген: позначений, але страва не заблокована
- рецепт: усі `{N}` підставились, жодного `{pXX}` у видимому тексті, жодного `p12` у полях для людини

Скрипт має друкувати діф до попереднього прогону. Без цього неможливо міняти промпти — ми в прототипі міняли наосліп і тричі ламали те, що працювало.

Промпти зберігати як версіоновані файли, не рядки в коді. Кожна відповідь моделі логується з версією промпту.

### Крок 1 — каталог інгредієнтів

Окремий сервіс і таблиця. Від нього залежать чотири механізми, і зараз кожен лікується милицею.

```sql
catalog_ingredient
  key              text primary key
  name             text
  aliases          text[]      -- як зустрічається в чеках і мовленні
  categories       text[]      -- ієрархія: мідії → молюски → морепродукти
  allergen_groups  text[]
  zone_default     text
  unit_weight      numeric     -- вага «однієї штуки»
  density          numeric
  nutrition        jsonb
```

Обсяг першої версії — 1500–2500 позицій українською. Джерела: каталоги мереж (назви як у чеках — найцінніше), відкриті бази продуктів, USDA для поживності.

**Критерій готовності — три тести, які зараз не проходять:**

1. алергія «молюски» позначає «Karolina — м'ясо мідій»
2. антипатерн «не їм свинину» позначає «Ковбаса Міланська»
3. пошук «кінзу» знаходить «кінза свіжа»

Заповнення каталогу — хороша задача для паралельних агентів із валідацією: один генерує, другий перевіряє проти джерел, третій ловить конфлікти категорій. Але спершу зроби схему й тести.

### Крок 2 — ядро

Postgres за схемою з `02-architecture.html`. Сервіси: chat, pantry, catalog, intake.

Що переносити з прототипу майже як є (воно перевірене на реальних даних):

- резолвер із трьома джерелами: посилання на партію → каталожний ключ → евристика
- каскад пошуку з ранньою зупинкою
- лагодження обрізаного JSON
- швидкий локальний ввід `+ молоко 1 л` — має працювати без мережі
- три компоненти карток: список зі `scope`, пропозиція, рецепт
- один канал уточнення через префікс у полі вводу

Що переробити:

- 51 стан у головному компоненті → стор із доменними зрізами
- оптимістичні оновлення з відкотом при помилці
- стрімінг відповіді замість очікування повного JSON
- зображення окремим запитом, а не в тілі повідомлення

**Cook Mode має працювати при поганому зв'язку.** Кроки й таймери локально, списання — в чергу. Людина стоїть біля плити, «немає інтернету» тут неприйнятне.

### Крок 3 — вкладення

Об'єктне сховище, стиснення на клієнті до 1400px, PDF як document-блок, черга вкладень, `temperature: 0`, повторний розбір із уточненням.

### Крок 4 — дім

`household` як головна одиниця власності. Спільне: комора, обладнання, список, календар. Особисте: профіль, досвід, журнал, сесії. Сесії не шеряться ніколи.

Тут же вирішити вартість: спільна комора йде в промпт кожному учаснику окремо. Або спільний кеш-префікс на рівні дому, або віддавати комору інструментом за запитом.

### Крок 5 — мережа

Інтерфейс `RetailProvider` із чотирма методами, не одна мережа. Сільпо — перша реалізація: `mcp.silpo.ua/mcp`, OAuth 2.1 + PKCE, токен тільки серверно.

## Метрики з першого дня

- частка інгредієнтів, зіставлених посиланням, а не назвою — головний показник здоров'я резолвера
- частка підтверджених операцій із запропонованих — нижче 70% означає, що модель домислює забагато
- скасувань після підтвердження
- токенів на активного користувача з розбивкою по профілях моделі
- час від відкриття до першої страви для нових
- **частка позицій, списаних як зіпсовані** — це головна обіцянка продукту, і саме її треба міряти до й після

## Чого не робити

**Не додавати екрани під кожну функцію.** Прототип пройшов шлях від дев'яти типів карток до трьох і від десяти секцій профілю до трьох. Кожне спрощення далося важче за додавання.

**Не виносити знання системи в плашки.** Тричі поспіль ми вішали те, що система знає, окремим блоком — чіпи «рятує», блок припущень, нагадування про задум — і тричі прибирали.

**Не підсилювати тривогу.** «Горить 11 позицій» знецінює себе за тиждень. Дві конкретні назви замість лічильника, словник без «терміново» й «пропаде».

**Не переставляти блоки в системному промпті.** Порядок сталий — від найстабільнішого до найзміннішого — і це умова префіксного кешування.

**Не знімати правила з промптів, не з'ясувавши, після якої помилки вони з'явились.** Реєстр збоїв у кінці `03-prompts.md`.

Прочитай `01-product.html` і `02-architecture.html`, потім `03-prompts.md`. Далі:

1. Запропонуй структуру репозиторію під описані сервіси
2. Зроби крок 0 цілком: фікстури, інваріанти, скрипт прогону, версіонування промптів
3. Покажи схему `catalog_ingredient` з десятком заповнених позицій, на яких проходять три критеріальні тести
4. Зупинись і покажи результат перед тим, як братись за ядро

Не починай із фіч. Спершу — те, чим їх перевіряти.
